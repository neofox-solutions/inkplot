# Locales and languages

Everything language-shaped in a chart is set in a few places, and none of it is built into the core: the library has no English strings, no translation tables and no locale data of its own. Numbers and dates come from the platform's `Intl`; words come from you.

| What | How | Where |
|---|---|---|
| Number format (grouping, decimal mark, digits) | `locale` on the chart, an axis, or a time scale; or a `format` function | [Numbers](#numbers) |
| Dates and time zones | A time scale's `locale`, `timeZone`, `weekStart` and `formats` | [Dates](#dates) |
| Reading direction | `direction="rtl"` on the chart | [Right to left](#right-to-left) |
| The words (titles, series names, summary, tooltip) | Plain attributes and functions you pass | [Words](#words) |
| An i18n framework | One function from your framework's state to chart options | [Recipe](#recipe-an-i18n-framework) |

## Numbers

`locale` is a BCP 47 tag (`'de'`, `'fr-CA'`, `'ar-EG'`). Set it on the `Chart` and every axis writes its numbers that language's way: `12 000,5` for `fr`, `12.000,5` for `de`, Arabic-Indic digits for `ar-EG`. The tooltip's coordinates follow, since they come from the same axes. `locale` on an axis beats the chart's, and a `format` function beats both.

With no `locale`, numbers are plain digits with a point, so a chart renders the same on every machine, including a server.

Anything that `Intl.NumberFormat` can do is a `format` away: currency, compact notation, units, percentages.

```ts check title="Currency and compact numbers on an axis"
import { Axis, LinearScale } from 'inkplot';

const eur = new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR', maximumFractionDigits: 0 });
const compact = new Intl.NumberFormat('en', { notation: 'compact' });

export const money = new Axis({ orientation: 'left', format: (v: number) => eur.format(v) }, new LinearScale());
export const big = new Axis({ orientation: 'right', format: (v: number) => compact.format(v) }, new LinearScale());
```

Make the formatter once, outside the function: building a `NumberFormat` per label is slow.

## Dates

A time scale takes timestamps in milliseconds and writes its ticks in `locale` (default: the chart's, else the platform's: a browser's own language in the DOM, `en-US` for a `StringPlatform` and so for `toSvgString`, whose `locale` option changes it), at the precision of the ticks, in `timeZone` (default `'UTC'`). The calendar, not a fixed width, decides where ticks fall, so months and daylight-saving days come out right. `weekStart` is 1 (Monday) unless you say otherwise; set 0 for Sunday, 6 for Saturday. `formats` replaces the format of one rank, as `Intl.DateTimeFormatOptions`.

```ts check title="A Japanese calendar axis in Tokyo time"
import { Axis, IntlTimeScale } from 'inkplot';

export const axis = new Axis(
  { orientation: 'bottom' },
  new IntlTimeScale({ locale: 'ja-JP', timeZone: 'Asia/Tokyo', weekStart: 0, formats: { month: { month: 'long' } } }),
);
```

The default `UTC` is deliberate: the same chart on a server in Virginia and a laptop in Sydney shows the same labels. Use `'local'` when the labels are meant to be the viewer's wall clock.

Other calendars come from the locale's extension (`'th-TH-u-ca-buddhist'`, `'ar-SA-u-ca-islamic'`). Where the tick positions should follow that calendar, rather than only its labels, write a time scale subclass: see [Custom data and scales](../extending/custom-data-and-scales.md#time-scales).

## Right to left

`direction="rtl"` on the `Chart` mirrors the layout defaults for Arabic, Hebrew and other right-to-left scripts:

- the first vertical axis is on the right, and a horizontal axis runs from the right, so the first category or the earliest date is at the right edge;
- a `Legend` or a colour or size key is on the left;
- a title starts at the right.

Anything you place yourself stays: an axis with an `orientation`, an `inverted` you set (even `inverted={false}`), a `side` on a legend.

It does **not** touch the text. The browser sets Arabic and Hebrew labels right to left whatever the chart's direction, and an SVG string is shaped by whatever shows it, so no font or shaping engine is involved. A label that mixes scripts (an Arabic name beside a Latin year) follows the left-to-right rules; put a right-to-left mark (U+200F) at its start for the other order. A legend row keeps its sample on the left of the name, and a polar plane keeps its angle running clockwise.

Cost: about 70 bytes gzipped, only for the chart that uses it; `direction` is `ltr` by default and nothing changes.

```tsx check title="A right-to-left chart with Arabic numerals and dates"
import { barChart, FlatDataSource, Legend, ChartTitle, lightTheme } from 'inkplot';

export const chart = barChart(
  [{ name: 'المبيعات', source: new FlatDataSource({ data: [4, 7, 5, 9], regularDomain: { start: 0, step: 1 } }) }],
  {
    theme: lightTheme,
    direction: 'rtl',
    locale: 'ar-EG',
    categories: ['الربع الأول', 'الربع الثاني', 'الربع الثالث', 'الربع الرابع'],
    extras: [new ChartTitle({ text: 'المبيعات حسب الربع' }), new Legend({})],
  },
);
```

Some locales are right to left in their dates only (a `ja` chart is left to right). `direction` and `locale` are independent: set both when you mean both.

## Words

The library says nothing in any language on its own. The places where words appear all take yours:

| Words | Where they come from |
|---|---|
| Chart title, axis titles, series names, legend entries | The `text`, `title` and `name` attributes you set. |
| The chart's accessible name and description | `meta` (`title`, `description`), or `ChartSummary` with your `text` and `roleDescription`. |
| Tooltip lines | `ChartTooltip`'s `format`. |
| Screen-reader announcements | The tooltip's `format` again: the live region says what the tooltip says. |

So translating a chart is changing the strings you pass, and nothing is shipped in a language you do not use. See [Accessibility](accessibility.md) for the summary and [Interaction](interaction.md) for the tooltip.

## Recipe: an i18n framework

Treat the chart as a function of the current language. Whatever your framework offers (i18next, react-intl, vue-i18n, Lingui, Angular's i18n, plain `Intl`) gives you three things: a **language tag**, a **text direction**, and **a way to look up a string**. Pass the three into a function that builds or updates the chart, and re-run it when the language changes.

```ts check title="A chart as a function of the language"
import { barChart, FlatDataSource, ChartTitle, Legend, ChartSummary, lightTheme } from 'inkplot';

interface Strings {
  language: string; // 'ar', 'de-CH'…
  dir: 'ltr' | 'rtl';
  t: (key: string) => string; // i18next's t, react-intl's formatMessage…
}

export function salesChart({ language, dir, t }: Strings, data: number[]) {
  return barChart([{ name: t('sales'), source: new FlatDataSource({ data, regularDomain: { start: 0, step: 1 } }) }], {
    theme: lightTheme,
    locale: language,
    direction: dir,
    categories: [t('q1'), t('q2'), t('q3'), t('q4')],
    extras: [
      new ChartTitle({ text: t('salesByQuarter') }),
      new Legend({}),
      new ChartSummary({ roleDescription: t('chart') }),
    ],
  });
}
```

How you get `dir` depends on the framework; with i18next it is `i18n.dir(language)`, and in a browser `Intl.Locale` can tell you too (`getTextInfo().direction` where it is available). A small table of the RTL scripts you support (`ar`, `he`, `fa`, `ur`) is also fine.

### When the language changes

- **Vanilla / `new`.** Detach the old chart and attach the result of calling the function again (sources belong to one chart, so build fresh ones). For a data-only update, keep the chart and set attributes: `chart.setAttributes({ locale, direction })` and the titles' `text`; the next flush redraws.
- **React.** With the wrappers, pass the values as props. With `ChartView`, call the function inside `useMemo` keyed on the language and give the result to it; `ChartView` attaches the chart while mounted and detaches it when it is not ([JSX, React and Web Components](frameworks.md#showing-a-chart-made-another-way)).
- **Server rendering.** Render with the request's language: `toSvgString(salesChart(strings, data), { width, height })`. The output has the same numbers the browser will write if you pass the same `locale`, as `Intl` data is the same on both sides for the locales your Node ships (use a Node with full ICU, which the default builds have).
- **Number formats the framework owns.** If your framework formats numbers (react-intl's `formatNumber`, i18next-icu), pass that as `format` on the axes and the tooltip, and the chart uses it everywhere; then `locale` on the chart only needs to match the dates.

Fonts are the one thing the chart cannot choose for you: the font a theme names has to include the script's glyphs (see [Styling](styling.md)). For Arabic, Hebrew, Devanagari and CJK, name a family that covers them, or rely on the platform's fallback. Text is measured with the platform's measurer, so a wider script lays out correctly in the browser; on a server, pass a `measureText` that matches your font ([Rendering](rendering.md)).
